danzlock — deadlock reversal diary

1. Anti-cheat Downgraded

2026-10-08 · build 6765 · source: UC thread 745313 (Hec4te, 2026-03-28 → 2026-08-06)

I expected something modern. Instead I found the same implementation Counter-Strike 2 uses — just switched off in most places. That's the first thing to understand: Deadlock's client-side anti-cheat isn't a new system, it's Valve's existing one with features disabled.

The client.dll does the work. There is no kernel driver. So before we write a single line of tooling, I want to map exactly what is running and what we must never touch.

Same AC as CS2 — but downgraded

The community consensus from the UnknownCheats thread, posted by Hec4te on 2026-03-28 and updated through August, is direct: the same as CS2 but downgraded. The mechanism lives inside the client binary. No kernel component ships with the game.

That means everything we need to worry about is in user-mode memory. It also means we know roughly what to expect — this stack was already dissected for Counter-Strike years ago.

What is active

MechanismDetail
Vtable checksDetects modification of interface vtables. Any detour, hook, or redirect on a known vtable trips it.
DllStatus protobufAVCUserMessage_DllStatus — sends the full list of loaded DLLs to Steam servers. Injection of any module becomes visible.
Inventory responseAVCUserMessage_Inventory_Response — a channel that also carries the late thread-scan report.
Thread scan (DllMain)Runs on DLL_THREAD_ATTACH. For each thread: checks if the start address is RWX, does not belong to any image, or sits inside kernel32/kernelbase. If it matches, the game reports: HMODULE, start address, memory protections, TID, return address, allocation base, 4 KB dump of the page, first bytes of NtOpenFile/LoadLibraryExW. Catches manual map AND LoadLibrary.

The thread scan is the sharpest tool here. As the research notes put it: it triggers both for manual map and loadlib. A DLL that normalises itself — maps its sections, restores permissions — still leaves a start address that does not belong to any mapped image. That is what catches stealthy loaders.

On the bypass question, the source is blunt: if you bypass what's sent from those protobufs [DllStatus + Inventory] you are essentially fully undetected (outside of CUserCmd tampering). We will not be bypassing anything. We will simply not be there.

What is off

  • VAC modules (streamed by Steam): OFF since Nov/Dec 2025 — both in Deadlock and CS2. I believe they will not come back at this point.
  • DLL file-integrity checking (which exists in CS2): disabled in Deadlock (modding community / early development).
  • No apparent VAC Live.

The combination is telling. The server-side behavioural system — the so-called frog — is what Valve is betting on. The client-side memory-forensics stack is a partial skeleton: module list and thread scan stay on, but VAC's file-integrity layer and the streamed modules are gone.

Bans: server-side, not memory

The only public ban vector anyone has documented is statistical. The author of the anti-cheat thread states it plainly: The only thing I ever got banned for was having a high headshot percentage.

That is the frog system. It watches play statistics on the server and acts on outliers. No memory evidence, no injection trace. This matches the broader theory that Valve's current strategy leans on server-side analysis and AI-driven pattern detection rather than kernel-level enforcement.

For our project the residual risk is not the tool — it is how the tool is used. A radar that automates play into absurd patterns is the vector. A read-only overlay that shows information is not.

Implication: strict read-only

Every active check maps to an operation we must never perform:

  1. Do not inject anything into the process — no DLL, no manual map, no shellcode, no remote thread.
  2. Do not open a write handle — read-only only (via KPRL, no handle at all).
  3. Do not modify vtables — pure reading.
  4. Behavioural detection (server-side) — the risk is usage, not the reading tool.

If a kernel anti-cheat or a new wave ever ships (the thread speculates they are working on a new AC), we revisit. Today there is no signal of any new active module.

2. GameEntitySystem — from disk to VA

2026-10-08 · build 6765 · client.dll 58,634,904 B · sha 1dc44d55…

The whole point of this series is to reverse Deadlock without running it. I sit on the other side of an anti-cheat that will flag the moment I attach a debugger or open a handle to the process. But the binary just sits there on disk, 58 megabytes of compiled C++, full of RIP-relative pointers waiting to be chased.

This post covers how I resolved GameEntitySystem — the global that owns every entity in the game — using nothing but a static pattern scanner, a hex editor, and two builds of client.dll. No debugger. No process handle. No game running.

The disk-first scanner

I wrote a tiny tool called tools/scan. It does exactly one thing: opens a PE file, reads it into memory, and searches for byte patterns. That's it. No process injection, no hooks, no OpenProcess. The entire attack surface is CreateFile + ReadFile on a DLL that Steam already put on my disk.

scan.exe "D:\SteamLibrary\steamapps\common\Deadlock\game\citadel\bin\win64\client.dll"   patterns-client.txt

The pattern format is dead simple — one byte per token, ? for wildcards:

NOME = 48 8B 0D ? ? ? ? 8B D0      # '?' or '??' = wildcard of 1 byte

When the scanner finds a match at some file offset, it converts that offset to an RVA, then to a VA by adding the image base (0x180000000). But the interesting part happens when the matched instruction is a RIP-relative memory access — the scanner goes one step further and resolves the target of that access.

RIP-resolve: mov vs lea

This is the single most important concept in the whole approach. x86-64 code doesn't use absolute addresses — they're not knowable at compile time because of ASLR. Instead the compiler emits RIP-relative instructions that compute address = address_of_next_instruction + disp32.

Two instructions look almost identical in a hex dump but mean completely different things:

48 8B 0D xx xx xx xx    mov  rcx, [rip+0x2067db9]   ; deref — rcx gets the VALUE at that address
48 8D 0D xx xx xx xx    lea  rcx, [rip+0x2067db9]   ; no deref — rcx IS the address

In mov reg, [rip+x], the register receives the pointer stored at the target address. That means the global itself contains a pointer to the real object, and you need one more deref at runtime. In lea reg, [rip+x], the register is the address — the global is the object (or the start of an array of objects).

The scanner's rip_target() function detects the common REX prefixes (48/4C), the opcode byte (8B = mov, 8D = lea, 89 = mov-store), and the ModR/M byte (05–3D with the right bit pattern for RIP-relative), then computes:

target = imageBase + rva_of_instruction + 7 + disp32

The +7 accounts for the instruction length (2-byte prefix+opcode, 1-byte ModR/M, 4-byte displacement). The rip-> annotation in the scan output tells you exactly this: the resolved VA of whatever the code is pointing at.

Three patterns, one target

For GameEntitySystem I had three completely independent byte patterns, each matching at a different location in the binary, each resolving to the exact same virtual address — RVA 0x3DB48B0, VA 0x183DB48B0:

[OK]   entity_list_dezlock        1 hit   RVA 0x2067DB9   rip->0x183DB48B0
[OK]   game_entity_system_alt     1 hit   RVA 0x16F3ABB   rip->0x183DB48B0
[OK]   game_entity_system_alt3    1 hit   RVA 0x206279A   rip->0x183DB48B0

These patterns come from different sources, contributed over months, in different code paths. The first one (entity_list_dezlock) was posted by dezlock back in March 2026. The other two (game_entity_system_alt and alt3) were added as "alternatives" on 6/10/2026 after the original game_entity_system pattern (from yfndream, June 2026) died in build 6759.

Here are the raw pattern definitions from tools/scan/patterns-client.txt:

Look at the ModR/M byte in the first byte of each pattern. The opcode is 89 (mov-store) in entity_list_dezlock — this code is writing a pointer into the global. The opcode is 8B (mov) in game_entity_system_alt and alt3 — they're reading from the global. Three different code paths, three different instruction encodings, one shared address. When patterns converge like this, you know you've got the right global.

ViewMatrix

Same approach, same confidence. The view_matrix pattern resolves to 0x183C7F960 (pattern RVA 0x18F3EE3):

[OK]   view_matrix                1 hit   RVA 0x18F3EE3   rip->0x183C7F960
[OK]   view_matrix_alt            1 hit   RVA 0x18F3EE3   rip->0x183C7F960

Both the primary and the alternate pattern match at the same RVA — they're two different instruction encodings for the same RIP-relative access. The primary pattern is a lea (compute the address), the alternate is a mov (read through it):

view_matrix             = 48 8D 0D ? ? ? ? 48 C1 E0 06
view_matrix_alt         = 48 8D ? ? ? ? ? 48 C1 E0 06 48 03 C1 C3

This is a high-confidence resolution. The view_matrix global stores a ViewMatrix_t — 4×4 floats that the game uses to transform world coordinates into clip space. The resolved target is RVA 0x3C7F960 (VA 0x183C7F960). Combined with screen_transform (RVA 0x18F9FD0), this is what an ESP or radar needs to draw on top of the game.

6763 → 6765: the −0x80 delta

I had a previous scan from build 6763 (out/scan-6763-client.txt). When the game patched from 6763 to 6765, I re-ran the scanner and diffed the results. The headline finding:

Global6763 VA6765 VADelta
GameEntitySystem0x183DB49300x183DB48B0−0x80
ViewMatrix0x183C7F9E00x183C7F960−0x80

Both globals moved by exactly −0x80 — 128 bytes downward. This kind of uniform shift usually means the compiler inserted a new global variable (or resized an existing one) somewhere in the same translation unit or in a linked object that gets laid out before these two. Everything else stayed put: trace_manager_global didn't move, create_move only shifted by 0x1C.

The pattern RVAs barely budged too. entity_list_dezlock went from RVA 0x2067BF9 (6763) to 0x2067DB9 (6765) — a +0x1C0 shift in the code, which is just the compiler adding a few instructions somewhere upstream. The resolved target moved by −0x80, meaning the data layout in the data section changed even though the code only shifted by +0x1C0.

This is exactly why pattern scanning is so powerful: you don't need to care why the address changed. You just re-run the scanner and get the new VA.

That's 23 unique hits, 2 multi-hits (ambiguous patterns), and 10 misses out of 37 patterns total. The three categories, and what each means in practice:

The original game_entity_system pattern, contributed by yfndream back in June 2026, is a MISS on both builds. The problem: 8B D0 is mov edx, eax — a fixed register pair with no wildcards. If the compiler ever swaps eax for ecx or reorders the surrounding instructions, the pattern breaks. The alternatives I use instead have more wildcards and are robust to minor instruction reordering:

# Dead (yfndream, jun/2026 — no wildcard on the mov edx, eax)
game_entity_system      = 48 8B 0D ? ? ? ? 8B D0 E8 ? ? ? ? 44 8B 83

# Alive (lote 2, added 10/06/2026 after the original died)
game_entity_system_alt   = 48 8B 1D ? ? ? ? 48 89 1D ? ? ? ? 4C 63 B3
game_entity_system_alt3  = 48 8B 05 ? ? ? ? 48 85 C0 0F 84 8B ? ? ? 48 8B 09

Same story for local_player_controller (from dezlock, March 2026) — MISS, replaced by local_player_alt_aw, local_player_alt_falz and local_player_sig2. And global_vars (with its fixed DC 00 00 00 displacement) was replaced by global_vars_v2 with full wildcards on the displacement.

The lesson: patterns are fragile. They work until the next compiler optimization or source change breaks them. That's why I always keep at least 2–3 independent patterns per critical global. When one dies, the others still resolve the same address. It's also why I keep a dated scan output in out/ — so I can diff two builds and see exactly what moved.

3. Entity chain — controller to bone

2026-10-08 · build 6765 · KPRL read-only · pid 4580

This is the third entry in the reversal diary. The previous section covered how the entity system global and view matrix were pinned to exact RVAs on disk. This one is about what happens after you have that pointer: the walk from a controller handle all the way to a bone position in screen space, without ever touching the process.

The problem

I need a bone — any bone — rendered at the right pixel on an overlay. The chain is long: entity system → chunk → identity → entity → pawn → scene node → bone array → bone. Every link is a pointer dereference through the KPRL driver, and every offset has to be exactly right or the whole thing reads garbage.

The approach that worked: resolve each hop from public schema sources, validate the first hop statically with tools/scan on the DLL from disk, then confirm the rest live with the reader attached to a running game. No injected dumper, no threads, no handles on the target.

Schema sources — never from an injected dumper

Rule from docs/04-schema-sources.md: every offset comes from deadworks.net/db/schema/client/<Class> or s2v.app/SchemaExplorer/deadlock/client. Both are maintained by the modding community from game files on disk. The advantage is that they survive builds — the schema is versioned per build, so when 6765 moved the entity system by −0x80 the diff is visible in db/changes.

The alternative — a runtime dumper injected into the game — would put a DLL and a thread inside the process. That is exactly what the anti-cheat watches (see section 1). External-only is not just cleaner, it is the only model that does not trip a single check.

Entity system → chunk → identity

Three independent patterns agree on the same target in client.dll build 6765:

PatternRVAVA
entity_list_dezlock0x2067DB90x183DB48B0
game_entity_system_alt0x16F3ABB0x183DB48B0
game_entity_system_alt30x206279A0x183DB48B0

The global at 0x183DB48B0 contains a pointer to CGameEntitySystem. From there:

CGameEntitySystem*  (deref global at 0x183DB48B0)
  +0x10  → chunks[8]   (8 chunk pointers)
  chunk = 512 entities × 0x70 bytes
  identity = chunks[idx >> 9] + 0x70 * (idx & 0x1FF)
  identity+0x00 → CEntityIdentity (m_pEntity)
  identity+0x10 → m_pEntity (CEntityInstance*)
  m_iHighestEntityIndex: +0x20C0

The reader code (src/app/game.cpp) actually validates up to 64 chunks (idx >> 9 <= 0x3F) as an upper bound, though the documented layout shows 8. Either way the walk is the same: index-shift to pick the chunk, mask to get the slot, multiply by 0x70 for the identity address.

Controller chain

The local player controller lives in an array at 0x183C342A0 (RVA 0x3C342A0, LEA). Slot zero is CCitadelPlayerController. The fields I need, all confirmed against the ~6753 schema dump:

OffsetFieldType
+0x6BCm_hPawnuint32 handle
+0x6FCm_iszPlayerNamechar[128] inline
+0x790m_bIsLocalPlayerControllerbool
+0x908m_PlayerDataGlobalinline struct
+0x1Cm_nHeroIDuint32 (inside PlayerDataGlobal)
+0x20m_nPreGameHeroIDuint32

The handle at +0x6BC is not a pointer — it is an index into the identity array. The mask 0x7FFF extracts the low 15 bits, and the reader double-checks that the identity's own index field matches before trusting the entity pointer. That is what makes the walk safe: a stale or corrupt handle resolves to nothing, not to a random address.

Pawn → scene node

Once the handle resolves to a C_BaseEntity, the fields that matter for a radar/ESP are:

OffsetFieldType
+0x330m_pGameSceneNodepointer
+0x350m_iMaxHealthint32
+0x354m_iHealthint32
+0x35Cm_lifeStateuint8
+0x3EFm_iTeamNumuint8
+0x400m_vecAbsVelocityVector (12 bytes)
+0x3C0m_flSimulationTimefloat

Velocity is read for prediction: if the pawn is moving, the aim lead is computed from m_vecAbsVelocity. The sanity check — reject any component over 10,000 — catches the case where the entity is dormant or the pointer is stale.

Scene node → bone array

The scene node is where position and bones live. The offsets changed from the old deadunlock layout:

OffsetFieldNote
+0xC8m_vecAbsOriginVectorWS — world position
+0xD4m_angAbsRotationQAngle
+0x103m_bDormantbool — networked = not visible
+0x1C0bone arraypointer — was 0x210 in deadunlock

The bone array pointer at sceneNode + 0x1C0 is the one that moved between engines. The old 0x210 offset produces garbage on build 6765; 0x1C0 was measured live and confirmed. Bones are laid out as:

boneArray = *(sceneNode + 0x1C0)
bone[i]  = boneArray + i * 0x20   (32 bytes per bone)
position = floats at bone+0x00, bone+0x04, bone+0x08

Not every index is a real bone — the reader reads up to 64 slots and discards any coordinate over 100,000 (world units), which filters out padding and uninitialised entries.

Entity chain diagram

World to screen

The view matrix is at 0x183C7F960 (pattern RVA 0x18F3EE3). It is a 4×4 float matrix read in one shot. The projection is straightforward:

clipX = x*m[0][0] + y*m[0][1] + z*m[0][2] + m[0][3]
clipY = x*m[1][0] + y*m[1][1] + z*m[1][2] + m[1][3]
clipW = x*m[3][0] + y*m[3][1] + z*m[3][2] + m[3][3]
if clipW < 0.1  → behind camera, reject
ndcX = clipX / clipW
ndcY = clipY / clipW
sx = (ndcX + 1) * 0.5 * width
sy = (1 − ndcY) * 0.5 * height

The clipW < 0.1 guard is the whole visibility test for a radar dot: if the point is behind the camera the projection flips and the screen coordinate is meaningless.

Live validation — pid 4580

The reader was attached to a running game (pid 4580, 1920×1080). Three known world positions were projected through the view matrix and came back as:

World positionScreen xScreen y
origin A689616
origin B648613
origin C747722

All three land inside the 1920×1080 viewport, which is the first sanity check. The second is that they move correctly when the camera rotates — a static projection would give the same numbers regardless of aim, but these tracked the player's look direction frame over frame.

What is not yet solved

  • Visibility. m_bDormant tells you whether the entity is networked, not whether a wall is in the way. A real vis check needs either the trace shape (internal only) or geometry parsed from the map files.
  • Bone indices for every hero. The table covers the common picks; new heroes ship with new indices.
  • FOW state. C_CitadelTeam::m_vecFOWEntities at +0x6C8 is the field, but its per-entity flag layout is not yet mapped.

4. Visibility — FOW is minimap

2026-10-08 · build 6765 · census 518 ents / 68 names · FOW zero team

I expected to find a wallhack flag. Instead I found a radar flag, and the difference matters more than I thought. This post is about what visibility actually means in Deadlock, what I measured, and why the answer is less powerful than the community assumed.

TraceShape: the right answer I can't use

The obvious path is TraceShape — the game's own raycast. dysonPeek mapped it back in October: RVA 0x16F5F40, a clean single-hit wrapper. The signature is in tools/scan/patterns-client.txt:

trace_shape_wrapper = 48 89 54 24 10 48 89 4C 24 08 55 53 56 57 41 54 41 56 41 57 48 8D AC 24 ? ? ? ? B8 ? ? 00 00

The 6765 scan confirms it — 1 hit at RVA 0x16F5F40. The pattern is alive. The layout is known: GameTrace_t with fraction+0xAC (visible > 0.97), bAllSolid+0xB6, masks SHOT/VISIBILITY 0x1C3003. Everything needed to call it is documented.

But calling TraceShape means executing game code inside the target process. That is injection — a thread, a call, a return address. The anti-cheat's thread scan (DllMain / DLL_THREAD_ATTACH) watches exactly for start addresses outside mapped images. The vtable checks watch for modified interface pointers. Calling a game function from outside touches both.

We are read-only. Not "read-only except when convenient." Strictly read-only. So TraceShape is off the table.

FOW: what I expected vs what is there

The entity chain doc says C_CitadelTeam+0x6C8 holds m_vecFOWEntities — an embedded UtlVector of STeamFOWEntity at +0x41. The name sounds like wallhack data: "FOW entities" = entities you can see through fog-of-war. I expected a per-target visibility flag.

I ran the census. The command walks all 8 entity chunks, reads identity headers, and tallies names:

danzlock.exe --fow

The output is blunt:

== censo: 518 entidades, 68 nomes ==
  ... (68 distinct names, zero of them "citadel_team_*") ...
== fim fow ==

518 entities. 68 distinct class names. Not a single citadel_team in the entity list. The FOW vector lives inside a team object that isn't even instantiated as a live entity in the way I expected. The census proves it: citadel_team is not a per-frame entity you can walk.

What FOW actually means

Page 64 of the UC thread clarifies it: FOW is the minimap radar, not a wallhack layer. It tells you "this unit is visible on the map", not "a bullet would reach this unit". The distinction is everything. A unit can be on your minimap (FOW says visible) but behind a wall (bullet blocked). FOW and occlusion are separate systems.

The game code confirms it. From game.cpp:

// ---- passo 4: FOW DESATIVADO (08/10): m_vecFOWEntities = minimapa, NAO parede.
// Censo ao vivo: citadel_team_* nem existe na entity list (518 ents, 68 nomes,
// zero team). FOW so diz "visivel no mapa", nunca "bala passa". Vischeck real
// = TraceShape (viola read-only) ou VPK raycast (projeto futuro).
// Visibilidade agora = dormant (rede) + filtros de mira (dist/FOV/sticky).
// visibleFow fica true p/ todos (neutro).

visibleFow stays true for everyone. Neutral. Useless as a wallhack. The FOW path is dead.

The occlusion experiment: what actually changes

If FOW is not the answer, what does change when a target goes behind a wall? I built a snapshot tool — --occl — that captures the raw bytes of a pawn and its scene node, then diffs two moments.

The usage is deliberate:

  1. Stand behind a wall with an enemy in your crosshair → danzlock.exe --occl a
  2. Step out so the enemy is visible → danzlock.exe --occl b
  3. Compare → danzlock.exe --occl diff

The diff logic reads 0x600 bytes of pawn and 0x130 bytes of scene node for each snapshot, then prints every byte that changed:

printf("-- PAWN bytes que MUDARAM --\n");
for (int off = 0; off < 0x600; ++off)
    if (A.pawn[off] != B.pawn[off])
        printf("  pawn+0x%03X: A=%02X B=%02X\n", off, A.pawn[off], B.pawn[off]);
printf("-- SCENENODE bytes que MUDARAM --\n");
for (int off = 0; off < 0x130; ++off)
    if (A.node[off] != B.node[off])
        printf("  node+0x%03X: A=%02X B=%02X\n", off, A.node[off], B.node[off]);

The result is the most honest data point in this post. Between "behind wall" and "visible", the only bytes that change in the pawn are animation timers:

pawn+0x2E8  — animation time
pawn+0x3BC  — animation cycle
pawn+0x3C0  — animation playback
pawn+0x3DC  — animation state

That is it. Four floats, all animation-related. No visibility flag. No occlusion boolean. No "can I shoot this" bit. The game does not store a per-target occlusion flag in the pawn that we can read.

What we actually use: dormant + behavioural filters

If there is no occlusion flag, how does the aim avoid shooting walls? Three layers, all read-only:

Layer 1 — network dormant

Every scene node has m_bDormant at +0x103. When the server stops sending updates about an entity, it goes dormant. A dormant entity is, by definition, not visible to you on the network. From game.cpp:

constexpr uint64_t SSN_DORMANT = 0x103;  // bool (m_bDormant, build 6763)

// in read_pawn_core:
uint8_t d = 0;
if (m_k.Read(m_pid, sceneNode + SSN_DORMANT, &d, 1)) p.dormant = (d != 0);

Dormant is a network-level "you don't know about this entity" flag. It is not occlusion — a unit can be visible on screen and dormant if the server hasn't told you about it yet. But it is a reliable negative: if dormant, you cannot see it.

Layer 2 — freeze-drop (350 ms)

When you are behind a wall, the server stops sending pose updates for the target. The bone position freezes. If the target is moving fast (> 50 units/s) but the bone has not moved for 350 ms, it is behind geometry. Drop the lock.

// aim.cpp — freeze-drop
} else if (vspd > 50.f && (now - st.lockFrozenSince) > 0.35f) {
    // corre mas o bone nao mexe ha 350ms = parede: SOLTA
    st.target = -1;
    st.targetPawn = 0;
    // ...
    break;
}

Layer 3 — w2s-miss (10 frames)

If WorldToScreen fails to project the bone for 10 consecutive frames, the target is behind the camera or inside geometry. Drop the lock.

// aim.cpp — w2s-miss
} else {
    // nao projeta 10 frames seguidos = parede/camera: SOLTA
    if (++st.lockMissW2s > 10) {
        st.target = -1;
        st.targetPawn = 0;
        // ...
        break;
    }
}

Together these three layers give a practical "don't shoot walls" filter without ever calling TraceShape and without reading a non-existent occlusion flag.

EyePosition: the honest origin

One more thing I got wrong before I measured it. I assumed the eye position for aim raycasts could come from m_vecViewOffset at +0xA88. It cannot. That field is quantized for network transmission — the client sends a compressed version to the server. Reading it from memory gives you the network-quantized value, not the render-accurate eye.

From game.cpp:

Vec3 Game::EyePosition(const PlayerData& p) {
    // Olho read-only: head bone em mundo; sem bones, origem + altura padrao.
    // (m_vecViewOffset e quantizado na rede — nao le confiavel de fora.)
    int hi = HeadBoneIndex(p.heroId);
    if (p.hasBones && hi >= 0 && hi < p.boneCount) return p.bones[hi];
    return Vec3{ p.origin.x, p.origin.y, p.origin.z + 64.f };
}

The eye is the head bone in world space. If bones are not available, fall back to origin + 64 units. The head bone is more accurate than any network-quantized view offset — it is the actual render position of the skull.

5. Aim — magnet, ease-out and CSV

2026-10-08 · build 6765 · n=2261 frames · src/app/aim.cpp

This is the post where the aim stops missing. Not because I tuned a magic number, but because I stopped fighting the engine and started measuring what "missing" actually means. The result is a three-layer system: world-velocity prediction that leads the target, a WindMouse curve that humanises the approach, and a sub-25px magnet that eases out with a smoothstep instead of snapping. Plus a CSV logger that told me exactly how wrong I was.

The problem with screen-space prediction

My first aim iteration did everything in screen space. Project the bone, measure the distance from centre, move the mouse. It worked — until the target strafed. Screen-space prediction lags one frame because you're always chasing the last projected position. The target moves, you see the new position a frame later, you move toward it. In a game where strafing is constant, that one-frame lag is the difference between a hit and a miss.

The fix is to predict in world space, where the target's velocity is a real 3D vector, not a 2D screen delta. The bone position comes from the pawn's scene node, and the velocity comes from ENT_VELOCITY at pawn offset +0x400. Multiply velocity by a capped lead time, add it to the bone position, then project to screen. The prediction travels with the target instead of chasing it.

Vec3 AimPointPredicted(const PlayerData& p, bool wantHead, int aimBone, float leadS) {
    Vec3 base = AimPointFor(p, wantHead, aimBone);
    if (leadS <= 0.0005f) return base;
    float spd = std::sqrt(p.velocity.x * p.velocity.x + p.velocity.y * p.velocity.y);
    if (spd < 1.f || spd > 1500.f) return base; // parado ou teleporte: sem lead
    float cap = leadS > 0.15f ? 0.15f : leadS;  // max 150ms de lead em mundo
    base.x += p.velocity.x * cap;
    base.y += p.velocity.y * cap;
    base.z += p.velocity.z * cap * 0.5f;
    return base;
}

Three guards here. Speed below 1 unit/s means the target is standing still — no lead. Speed above 1500 means teleport or network correction — no lead. And the lead time itself is capped at 150ms no matter what the preset asks for, because beyond that you're predicting into noise.

Screen EMA: killing the jitter

World prediction solves the strafe lag, but it introduces a new problem: the projected point jitters. Hitboxes are thin, bones oscillate by a pixel or two, and a raw projection makes the aim look nervous. I added a 65/35 exponential moving average on the screen point — 65% new position, 35% previous smoothed position.

if (!st.smInit) {
    st.smX = wantX; st.smY = wantY; st.smInit = true;
} else {
    float jx = wantX - st.smX, jy = wantY - st.smY;
    float jd = std::sqrt(jx * jx + jy * jy);
    if (jd > 150.f) {
        st.smX = wantX; st.smY = wantY; // salto grande = troca real: cola direto
    } else {
        st.smX = st.smX * 0.35f + wantX * 0.65f;
        st.smY = st.smY * 0.35f + wantY * 0.65f;
    }
}

The 150px jump threshold is the escape hatch. If the target teleports or the lock switches to a different player, the EMA would drag the aim across the screen. Above 150px, snap directly. Below it, smooth.

Velocity EMA with bias correction

The screen EMA smooths position, but I also need velocity for the sticky prediction (when the target drops behind a wall, I extrapolate from the last known position). A naive velocity calculation — (current - last) / dt — is noisy. A 50/50 EMA on velocity helps, but it has a known bias: in constant strafe, the EMA lags to one side of the true velocity vector, which makes the aim drift left or right of the target.

The fix is a bias correction term. After the EMA update, add 25% of the difference between the raw velocity and the EMA velocity:

float k = 0.5f;
st.lastVelX = st.lastVelX * (1.f - k) + vx * k + (vx - st.lastVelX) * 0.25f;
st.lastVelY = st.lastVelY * (1.f - k) + vy * k + (vy - st.lastVelY) * 0.25f;

This is a standard EMA bias correction (the same technique used in TCP RTT estimation). The +0.25f term pulls the EMA toward the current sample faster when the velocity is changing, killing the lateral drift.

WindMouse: the humaniser

Once the target point is computed, the mouse needs to move toward it in a way that doesn't look like a robot. A straight lerp is too perfect. A pure random walk is too slow. WindMouse sits in between: a gravity term pulls toward the target, a wind term adds controlled noise, and the whole thing is scaled by an adaptive smooth factor.

float dist = distC < 1.f ? 1.f : distC;
float grav = distC > 200.f ? 10.f : (distC > 60.f ? 12.f : 15.f);
float windMag = 1.5f + cfg.aimHumanize * 5.f; // 1.5 (gruda) .. 6.5 (curvo)
float wCur = windMag < dist ? windMag : dist;
const float kSqrt3 = 1.7320508f, kSqrt5 = 2.2360679f;
if (dist >= 30.f) {
    float r1 = (float)std::rand() / (float)RAND_MAX;
    float r2 = (float)std::rand() / (float)RAND_MAX;
    st.windX = st.windX / kSqrt3 + (2.f * r1 - 1.f) * wCur / kSqrt5;
    st.windY = st.windY / kSqrt3 + (2.f * r2 - 1.f) * wCur / kSqrt5;
} else {
    st.windX = st.windX / kSqrt3;
    st.windY = st.windY / kSqrt3;
}
float vx = st.windX + grav * (aimX - cx) / dist;
float vy = st.windY + grav * (aimY - cy) / dist;

The gravity is distance-dependent: 15 within 60px, 12 from 60–200px, 10 beyond 200px. Closer targets get pulled harder (you want to land the hit), distant targets get a gentler pull (you want to approach naturally). The wind magnitude scales with aimHumanize — 0.1 gives a nearly straight line, 0.55 gives a visibly curved approach.

Adaptive smooth adjusts the step size based on target speed:

float smooth = cfg.aimSmooth < 1.f ? 1.f : cfg.aimSmooth;
float tgtSpd = std::sqrt(st.lastVelX * st.lastVelX + st.lastVelY * st.lastVelY);
if (tgtSpd > 500.f) smooth *= 0.6f;       // alvo rapido: gruda junto
else if (distC < 60.f) smooth *= 1.2f;    // perto (fora do ima): leve
vx /= smooth; vy /= smooth;

Fast target (>500 px/s) gets a tighter smooth (0.6×) to keep up. Close target (<60px, outside the magnet zone) gets a looser smooth (1.2×) for fine adjustment. The final step is capped by aimMaxStep to prevent single-frame jumps.

The magnet: sub-25px ease-out

This is the part that took the most iterations. When the crosshair is within 25px of the target, the WindMouse gravity is too aggressive — it overshoots, oscillates, and looks like a snap. But doing nothing means the aim never quite centres. The answer is a smoothstep ease-out on the pure bone position (no screen lead, no prediction — just centre).

if (distC < 25.f) {
    float px = wantX, py = wantY; // ponto PURO do bone (sem lead de tela)
    float pdx = px - cx, pdy = py - cy;
    float pdist = std::sqrt(pdx * pdx + pdy * pdy);
    if (pdist < cfg.aimDeadzone) { /* parado */ return; }
    float t = pdist / 25.f;
    if (t > 1.f) t = 1.f;
    float ease = t * t * (3.f - 2.f * t); // smoothstep
    float gain = 0.12f + 0.55f * ease;    // 12%..67% da distancia
    float mx = pdx * gain, my = pdy * gain;
    float mm = std::sqrt(mx * mx + my * my);
    if (mm > 14.f) { mx *= 14.f / mm; my *= 14.f / mm; }
    // sub-pixel carry
    st.windX += mx - (float)((int)mx);
    st.windY += my - (float)((int)my);
    float ix = (float)((int)mx), iy = (float)((int)my);
    if (std::fabs(st.windX) >= 1.f) {
        float carry = (float)((int)st.windX);
        ix += carry; st.windX -= carry;
    }
    if (std::fabs(st.windY) >= 1.f) {
        float carry = (float)((int)st.windY);
        iy += carry; st.windY -= carry;
    }
    MoveMouse(ix, iy);
}

The gain curve is a smoothstep from 12% to 67% of the remaining distance. At 25px out, you move 67% of the way — aggressive enough to close fast. At 5px out, you move ~18% — gentle enough to land without overshoot. The 14px cap prevents a single large jump even at the edge of the magnet zone.

The subpixel carry is the detail that makes it feel human. Without it, a 0.8px move truncates to 0 and the aim stalls just outside the deadzone. With it, the fractional part accumulates in st.windX/st.windY until it crosses 1.0, then gets emitted as an extra pixel. The result is a smooth, continuous approach that never quite stops moving.

The curve is flat near zero (small corrections are gentle) and steep near 25px (large corrections are aggressive). This is the opposite of a linear gain, which would feel twitchy at range and sluggish up close.

Sticky lock: pawn-based, not index-based

Target switching is the silent killer of aim quality. If the aim re-evaluates "who is closest to centre" every frame, it flickers between targets during strafes. The fix is a sticky lock: once a target is acquired, keep it until it dies, goes dormant, or drops behind a wall.

The lock is keyed by pawn pointer, not entity index. Indices reuse; pawns don't. When the locked pawn is found in the player list, the aim checks three conditions before releasing:

  1. Validity: pawn still in list, not local, not same team, alive, not dormant (if aimVisibleOnly).
  2. Frozen bone: if the 3D bone position hasn't moved more than 2 units in 350ms while the target's velocity is above 50 units/s, the target is behind a wall — the server stopped sending pose updates. Release.
  3. Projection miss: if WorldToScreen fails for 10 consecutive frames, the target is off-screen or occluded. Release.

When the lock is lost but the target was seen recently (within aimStickyMs), the aim extrapolates from the last known position using the velocity EMA. This keeps the crosshair on the target through brief occlusions instead of snapping to centre.

The hysteresis bonus prevents flicker: when evaluating candidates, the current lock gets a 25% distance bonus (0.75² on the squared distance). A new target must be significantly closer to centre to steal the lock.

The dx=17.2 figure is the average distance from centre across all frames — most of which are in the WindMouse zone, where the aim is still travelling. The IMA zone is only active for the last 25px, but that's where the hit registers.

The zones are concentric. The deadzone (2–6px depending on preset) is where the aim does nothing. The magnet zone (0–25px) is where the ease-out takes over. The near zone (25–60px) is where WindMouse gravity is 15 and the smooth is 1.2×. The far zone (60–200px) is where gravity drops to 12 and the smooth is 1.0×. Beyond 200px, gravity is 10 and the smooth drops to 0.6× if the target is moving fast.

INI save/load

The settings persist through a simple INI file at %TEMP%\danzlock.ini. The save is a single fprintf with all fields; the load is a line-by-line sscanf_s that applies the preset first, then lets individual sliders override it. This means you can save a custom config that starts from a preset but tweaks one or two values.

// Save: one fprintf with all fields
fprintf(f,
    "preset=%d\nbone=%d\neye=%d\nkey=%d\n"
    "fov=%.1f\nsmooth=%.2f\nmaxstep=%.1f\npredict=%.1f\nreact=%.1f\n"
    "deadzone=%.2f\nhumanize=%.2f\nheadprob=%.2f\n"
    "sticky=%d\nstickyms=%.1f\nstickypx=%.1f\nvisonly=%d\nsnaphead=%d\n"
    "esp=%d\nskel=%d\nheadot=%d\nhealth=%d\nname=%d\nhero=%d\n"
    "esplocal=%d\nnamesize=%.1f\nespvis=%d\ndim=%d\neyeline=%d\ndrawfov=%d\n",
    s.aimPreset, s.aimBone, s.aimEyeMode, s.aimKey, ...);

// Load: preset first, sliders override
if (sscanf_s(line, "preset=%d", &iv) == 1) {
    if (iv >= 0 && iv < kAimPresetCount) ApplyAimPreset(s, (AimPreset)iv);
    continue;
}
if (sscanf_s(line, "fov=%f", &fv) == 1) { s.aimFov = fv; continue; }
// ... same pattern for every field

The load order matters: preset is parsed first and calls ApplyAimPreset, which sets all the aim fields to the preset defaults. Then individual keys like fov and smooth override those defaults. The result is a config that says "start from Equilibrado but with FOV 90 and humanize 0.4" without needing to specify every field.

What I'd do differently

The world prediction is capped at 150ms, but the presets ask for 120–140ms. That's fine — the cap is a safety rail, not a target. But the screen lead cap of 120px is arbitrary. A better cap would be proportional to the target's angular velocity, not a fixed pixel count. At 1080p, 120px is about 6° of rotation; at 4K, it's 3°. The cap should scale with resolution.

The WindMouse gravity values (10/12/15) are tuned by feel. The CSV logger gives me the data to tune them analytically — I can measure the overshoot distribution and adjust the gravity to minimise it. That's the next iteration.

The subpixel carry works, but it's a hack. A better approach would be to accumulate the mouse delta in a floating-point variable and only emit integer moves when the accumulator crosses 1.0. That's essentially what the code does, but it's spread across windX/windY which are also used for the WindMouse state. Separating the accumulator from the wind state would make the code clearer.
