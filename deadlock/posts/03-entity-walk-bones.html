Walking Entities Externally: Controller to Bone

2026-10-08 · build 6765 · KPRL read-only

This is the third entry in the reversal diary. The previous post covered how the entity system global and view matrix were pinned to exact RVAs on disk. This one is about what happens after you have that pointer: the walk from a controller handle all the way to a bone position in screen space, without ever touching the process.

The problem

I need a bone — any bone — rendered at the right pixel on an overlay. The chain is long: entity system → chunk → identity → entity → pawn → scene node → bone array → bone. Every link is a pointer dereference through the KPRL driver, and every offset has to be exactly right or the whole thing reads garbage.

The approach that worked: resolve each hop from public schema sources, validate the first hop statically with tools/scan on the DLL from disk, then confirm the rest live with the reader attached to a running game. No injected dumper, no threads, no handles on the target.

Schema sources — never from an injected dumper

Rule from docs/04-schema-sources.md: every offset comes from deadworks.net/db/schema/client/<Class> or s2v.app/SchemaExplorer/deadlock/client. Both are maintained by the modding community from game files on disk. The advantage is that they survive builds — the schema is versioned per build, so when 6765 moved the entity system by −0x80 the diff is visible in db/changes.

The alternative — a runtime dumper injected into the game — would put a DLL and a thread inside the process. That is exactly what the anti-cheat watches (see docs/01-anticheat.md). External-only is not just cleaner, it is the only model that does not trip a single check.

Entity system → chunk → identity

Three independent patterns agree on the same target in client.dll build 6765:

PatternRVAVA
entity_list_dezlock0x2067DB90x183DB48B0
game_entity_system_alt0x16F3ABB0x183DB48B0
game_entity_system_alt30x206279A0x183DB48B0

The global at 0x183DB48B0 contains a pointer to CGameEntitySystem. From there:

CGameEntitySystem*  (deref global at 0x183DB48B0)
  +0x10  → chunks[8]   (8 chunk pointers)
  chunk = 512 entities × 0x70 bytes
  identity = chunks[idx >> 9] + 0x70 * (idx & 0x1FF)
  identity+0x00 → CEntityIdentity (m_pEntity)
  identity+0x10 → m_pEntity (CEntityInstance*)
  m_iHighestEntityIndex: +0x20C0

The reader code (src/app/game.cpp) actually validates up to 64 chunks (idx >> 9 <= 0x3F) as an upper bound, though the documented layout shows 8. Either way the walk is the same: index-shift to pick the chunk, mask to get the slot, multiply by 0x70 for the identity address.

Controller chain

The local player controller lives in an array at 0x183C342A0 (RVA 0x3C342A0, LEA). Slot zero is CCitadelPlayerController. The fields I need, all confirmed against the ~6753 schema dump:

OffsetFieldType
+0x6BCm_hPawnuint32 handle
+0x6FCm_iszPlayerNamechar[128] inline
+0x790m_bIsLocalPlayerControllerbool
+0x908m_PlayerDataGlobalinline struct
+0x1Cm_nHeroIDuint32 (inside PlayerDataGlobal)
+0x20m_nPreGameHeroIDuint32

The handle at +0x6BC is not a pointer — it is an index into the identity array. The mask 0x7FFF extracts the low 15 bits, and the reader double-checks that the identity's own index field matches before trusting the entity pointer. That is what makes the walk safe: a stale or corrupt handle resolves to nothing, not to a random address.

Pawn → scene node

Once the handle resolves to a C_BaseEntity, the fields that matter for a radar/ESP are:

OffsetFieldType
+0x330m_pGameSceneNodepointer
+0x350m_iMaxHealthint32
+0x354m_iHealthint32
+0x35Cm_lifeStateuint8
+0x3EFm_iTeamNumuint8
+0x400m_vecAbsVelocityVector (12 bytes)
+0x3C0m_flSimulationTimefloat

Velocity is read for prediction: if the pawn is moving, the aim lead is computed from m_vecAbsVelocity. The sanity check — reject any component over 10 000 — catches the case where the entity is dormant or the pointer is stale.

Scene node → bone array

The scene node is where position and bones live. The offsets changed from the old deadunlock layout:

OffsetFieldNote
+0xC8m_vecAbsOriginVectorWS — world position
+0xD4m_angAbsRotationQAngle
+0x103m_bDormantbool — networked = not visible
+0x1C0bone arraypointer — was 0x210 in deadunlock

The bone array pointer at sceneNode + 0x1C0 is the one that moved between engines. The old 0x210 offset produces garbage on build 6765; 0x1C0 was measured live and confirmed. Bones are laid out as:

boneArray = *(sceneNode + 0x1C0)
bone[i]  = boneArray + i * 0x20   (32 bytes per bone)
position = floats at bone+0x00, bone+0x04, bone+0x08

Not every index is a real bone — the reader reads up to 64 slots and discards any coordinate over 100 000 (world units), which filters out padding and uninitialised entries.

World to screen

The view matrix is at 0x183C7F960 (RVA 0x3C7F960). It is a 4×4 float matrix read in one shot. The projection is straightforward:

clipX = x*m[0][0] + y*m[0][1] + z*m[0][2] + m[0][3]
clipY = x*m[1][0] + y*m[1][1] + z*m[1][2] + m[1][3]
clipW = x*m[3][0] + y*m[3][1] + z*m[3][2] + m[3][3]
if clipW < 0.1  → behind camera, reject
ndcX = clipX / clipW
ndcY = clipY / clipW
sx = (ndcX + 1) * 0.5 * width
sy = (1 − ndcY) * 0.5 * height

The clipW < 0.1 guard is the whole visibility test for a radar dot: if the point is behind the camera the projection flips and the screen coordinate is meaningless.

Live validation — pid 11816

The reader was attached to a running game (pid 11816, 1920×1080). Three known world positions were projected through the view matrix and came back as:

World positionScreen xScreen y
origin A689616
origin B648613
origin C747722

All three land inside the 1920×1080 viewport, which is the first sanity check. The second is that they move correctly when the camera rotates — a static projection would give the same numbers regardless of aim, but these tracked the player's look direction frame over frame.

Scan summary — build 6765

The static scan of client.dll from disk produced:

  • 23 patterns with a unique hit
  • 2 patterns with multiple hits (camera_manager, game_entity_system_alt2 — the latter is a 22-hit noise pattern, discarded)
  • 10 patterns missed entirely (old signatures that died with the map update)

client.dll: 58 634 904 bytes, sha256 prefix 1dc44d55…. The 6765 update moved the entity system by −0x80 and the view matrix by −0x80 — small shifts, but enough to kill any hardcoded address from 6763.

What is not yet solved

  • Visibility. m_bDormant tells you whether the entity is networked, not whether a wall is in the way. A real vis check needs either the trace shape (internal only) or geometry parsed from the map files.
  • Bone indices for every hero. The table covers the common picks; new heroes ship with new indices.
  • FOW state. C_CitadelTeam::m_vecFOWEntities at +0x6C8 is the field, but its per-entity flag layout is not yet mapped.
