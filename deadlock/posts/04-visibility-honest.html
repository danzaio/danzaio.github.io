Visibility, Honestly: FOW Is Minimap

I expected to find a wallhack flag. Instead I found a radar flag, and the difference matters more than I thought. This post is about what visibility actually means in Deadlock, what I measured, and why the answer is less powerful than the community assumed.

TraceShape: the right answer I can't use

The obvious path is TraceShape — the game's own raycast. dysonPeek mapped it back in October: RVA 0x16F5F40, a clean single-hit wrapper. The signature is in tools/scan/patterns-client.txt:

trace_shape_wrapper = 48 89 54 24 10 48 89 4C 24 08 55 53 56 57 41 54 41 56 41 57 48 8D AC 24 ? ? ? ? B8 ? ? 00 00

The 6765 scan confirms it — 1 hit at RVA 0x16F5F40. The pattern is alive. The layout is known: GameTrace_t with fraction+0xAC (visible > 0.97), bAllSolid+0xB6, masks SHOT/VISIBILITY 0x1C3003. Everything needed to call it is documented.

But calling TraceShape means executing game code inside the target process. That is injection — a thread, a call, a return address. The anti-cheat's thread scan (DllMain / DLL_THREAD_ATTACH) watches exactly for start addresses outside mapped images. The vtable checks watch for modified interface pointers. Calling a game function from outside touches both.

We are read-only. Not "read-only except when convenient." Strictly read-only. So TraceShape is off the table.

FOW: what I expected vs what is there

The entity chain doc says C_CitadelTeam+0x6C8 holds m_vecFOWEntities — an embedded UtlVector of STeamFOWEntity at +0x41. The name sounds like wallhack data: "FOW entities" = entities you can see through fog-of-war. I expected a per-target visibility flag.

I ran the census. The command walks all 8 entity chunks, reads identity headers, and tallies names:

danzlock.exe --fow

The output is blunt:

== censo: 518 entidades, 68 nomes ==
  ... (68 distinct names, zero of them "citadel_team_*") ...
== fim fow ==

518 entities. 68 distinct class names. Not a single citadel_team in the entity list. The FOW vector lives inside a team object that isn't even instantiated as a live entity in the way I expected. The census proves it: citadel_team is not a per-frame entity you can walk.

What FOW actually means

Page 64 of the UC thread clarifies it: FOW is the minimap radar, not a wallhack layer. It tells you "this unit is visible on the map", not "a bullet would reach this unit". The distinction is everything. A unit can be on your minimap (FOW says visible) but behind a wall (bullet blocked). FOM and occlusion are separate systems.

The game code confirms it. From game.cpp:

// ---- passo 4: FOW DESATIVADO (08/10): m_vecFOWEntities = minimapa, NAO parede.
// Censo ao vivo: citadel_team_* nem existe na entity list (518 ents, 68 nomes,
// zero team). FOW so diz "visivel no mapa", nunca "bala passa". Vischeck real
// = TraceShape (viola read-only) ou VPK raycast (projeto futuro).
// Visibilidade agora = dormant (rede) + filtros de mira (dist/FOV/sticky).
// visibleFow fica true p/ todos (neutro).

visibleFow stays true for everyone. Neutral. Useless as a wallhack. The FOW path is dead.

The occlusion experiment: what actually changes

If FOW is not the answer, what does change when a target goes behind a wall? I built a snapshot tool — --occl — that captures the raw bytes of a pawn and its scene node, then diffs two moments.

The usage is deliberate:

  1. Stand behind a wall with an enemy in your crosshair → danzlock.exe --occl a
  2. Step out so the enemy is visible → danzlock.exe --occl b
  3. Compare → danzlock.exe --occl diff

The diff logic reads 0x600 bytes of pawn and 0x130 bytes of scene node for each snapshot, then prints every byte that changed:

printf("-- PAWN bytes que MUDARAM --\n");
for (int off = 0; off < 0x600; ++off)
    if (A.pawn[off] != B.pawn[off])
        printf("  pawn+0x%03X: A=%02X B=%02X\n", off, A.pawn[off], B.pawn[0]);
printf("-- SCENENODE bytes que MUDARAM --\n");
for (int off = 0; off < 0x130; ++off)
    if (A.node[off] != B.node[off])
        printf("  node+0x%03X: A=%02X B=%02X\n", off, A.node[off], B.node[0]);

The result is the most honest data point in this post. Between "behind wall" and "visible", the only bytes that change in the pawn are animation timers:

pawn+0x2E8  — animation time
pawn+0x3BC  — animation cycle
pawn+0x3C0  — animation playback
pawn+0x3DC  — animation state

That is it. Four floats, all animation-related. No visibility flag. No occlusion boolean. No "can I shoot this" bit. The game does not store a per-target occlusion flag in the pawn that we can read.

What we actually use: dormant + behavioural filters

If there is no occlusion flag, how does the aim avoid shooting walls? Three layers, all read-only:

Layer 1 — network dormant

Every scene node has m_bDormant at +0x103. When the server stops sending updates about an entity, it goes dormant. A dormant entity is, by definition, not visible to you on the network. From game.cpp:

constexpr uint64_t SSN_DORMANT = 0x103;  // bool (m_bDormant, build 6763)

// in read_pawn_core:
uint8_t d = 0;
if (m_k.Read(m_pid, sceneNode + SSN_DORMANT, &d, 1)) p.dormant = (d != 0);

Dormant is a network-level "you don't know about this entity" flag. It is not occlusion — a unit can be visible on screen and dormant if the server hasn't told you about it yet. But it is a reliable negative: if dormant, you cannot see it.

Layer 2 — freeze-drop (350 ms)

When you are behind a wall, the server stops sending pose updates for the target. The bone position freezes. If the target is moving fast (> 50 units/s) but the bone has not moved for 350 ms, it is behind geometry. Drop the lock.

// aim.cpp — freeze-drop
} else if (vspd > 50.f && (now - st.lockFrozenSince) > 0.35f) {
    // corre mas o bone nao mexe ha 350ms = parede: SOLTA
    st.target = -1;
    st.targetPawn = 0;
    // ...
    break;
}

Layer 3 — w2s-miss (10 frames)

If WorldToScreen fails to project the bone for 10 consecutive frames, the target is behind the camera or inside geometry. Drop the lock.

// aim.cpp — w2s-miss
} else {
    // nao projeta 10 frames seguidos = parede/camera: SOLTA
    if (++st.lockMissW2s > 10) {
        st.target = -1;
        st.targetPawn = 0;
        // ...
        break;
    }
}

Together these three layers give a practical "don't shoot walls" filter without ever calling TraceShape and without reading a non-existent occlusion flag.

EyePosition: the honest origin

One more thing I got wrong before I measured it. I assumed the eye position for aim raycasts could come from m_vecViewOffset at +0xA88. It cannot. That field is quantized for network transmission — the client sends a compressed version to the server. Reading it from memory gives you the network-quantized value, not the render-accurate eye.

From game.cpp:

Vec3 Game::EyePosition(const PlayerData& p) {
    // Olho read-only: head bone em mundo; sem bones, origem + altura padrao.
    // (m_vecViewOffset e quantizado na rede — nao le confiavel de fora.)
    int hi = HeadBoneIndex(p.heroId);
    if (p.hasBones && hi >= 0 && hi < p.boneCount) return p.bones[hi];
    return Vec3{ p.origin.x, p.origin.y, p.origin.z + 64.f };
}

The eye is the head bone in world space. If bones are not available, fall back to origin + 64 units. The head bone is more accurate than any network-quantized view offset — it is the actual render position of the skull.

Summary: what visibility is and isn't

WhatReality
FOW (m_vecFOWEntities)Minimap radar, not wallhack. citadel_team not in entity list (518 ents, 68 names, zero team). visibleFow stays true — neutral.
Occlusion flagDoes not exist in pawn. Diff shows only animation timers change (+0x2E8/+0x3BC/+0x3C0/+0x3DC).
TraceShapeCorrect answer, wrong method. Calling game fn = injection = detected.
Dormant (+0x103)Network-level "not visible" flag. Reliable negative.

w2s-miss (10 f)Cannot project = behind camera/geometry.

The honest answer is that there is no wallhack flag to read. There is a radar flag (FOW), a network flag (dormant), and two behavioural heuristics (freeze-drop, w2s-miss). That is what we have. It is less than I hoped and more than nothing.
